# Сверка платежей и подготовка обновления сервера

Этот этап **не включает новую модель 27% для реальных заказов**, не подключает Консоль.Про и не делает систему готовой к реальным деньгам. Изменения не развёрнуты автоматически. Не включайте реальные платежи или новую договорную схему без проверки `docs/06_release_readiness.md` и `docs/07_refund_safety_hold.md`.

## Новая вкладка «Сверка платежей»

В `/admin` владелец и администратор могут открыть список заказов с локальными признаками риска: расхождение суммы заказа с записями успешных платежей, просроченный ожидающий платёж, отмена при платеже, подозрительные записи возврата и необходимость проверки чека. Строка содержит только локальные суммы и ссылку на существующую карточку заказа. Сторонние сервисы не вызываются, данные не изменяются. Платежи подписок не входят в отчёт.

Страница проверяет до 100 заказов за раз в порядке убывания номера; используйте «Более старые заказы», чтобы не пропустить историю. Результаты не являются полным мониторингом базы или снимком в одной транзакции: одновременно меняющиеся записи могут дать временное предупреждение — обновите и сравните. Отсутствие предупреждений не подтверждает отсутствие оплаты у провайдера, выдачу чека или возврат. Все чеки успешных платежей и все имеющиеся записи возвратов требуют внешней проверки, в том числе старые локальные отметки `issued`/`succeeded`. Ожидание после локального истечения срока **не означает**, что платёж отменён. Оператор проверяет платёж, возврат и чек по идентификаторам в карточке заказа и первичным данным провайдера. Не выполняйте повторный возврат до сверки исхода предыдущего.

## Защита доступа и совместимость

- Отсутствующий или пустой `MAX_WEBHOOK_SECRET` больше не разрешает webhook. Если на сервере он пустой, сообщения MAX перестанут обрабатываться после обновления. До обновления проверьте наличие секрета, что он не тестовый или шаблонный, и фактическую регистрацию webhook, не выводя и не передавая секрет. Менять секрет в приложении отдельно от настроек MAX нельзя.
- CORS по умолчанию не разрешает запросы со сторонних сайтов. Существующие сайт и админка на том же origin работают без дополнительной настройки. При наличии другого согласованного фронтенда можно указать **точные** адреса через `CORS_ALLOWED_ORIGINS=https://frontend.example.ru` (несколько через запятую); `*` запрещён. Чужие вебхуки MAX и ЮKassa — серверные запросы и от CORS не зависят. CORS не заменяет защиту от CSRF, а также не решает вопросы доверенных прокси, ACL и безопасности админки.
- Перед включением любых реальных платежей дополнительно проверить, что обратный прокси перезаписывает входящие заголовки IP (в том числе `X-Real-IP`), порт API не доступен напрямую извне, входящие webhook защищены, что деньги сверяются с реальным провайдером, а схема чеков подтверждена.

## Безопасная проверка текущего VPS перед обновлением

Если подключаетесь к существующему серверу как `root`, с Mac выполните `ssh root@136.234.157.231`; иначе используйте обычную учётную запись и адрес вашего сервера. На сервере выполните приведённые команды. Они не читают и не показывают значения ключей, но показывают статус сервисов и название/хост БД. Не присылайте `.env`, содержимое дампов, токены, пароли, номера клиентов или логи с персональными данными.

```bash
cd /opt/sneg
pwd
git status -sb
git log -1 --oneline
docker compose ps
docker compose exec -T api python -c 'from src.core.config import get_settings; from sqlalchemy.engine import make_url; s=get_settings(); u=make_url(s.database_url); print("environment:",s.app_env,"messenger:",s.messenger_transport,"simulator:",s.enable_simulator,"payments:",s.payment_provider,"storage:",s.storage_provider); print("DB:",u.drivername,"host:",u.host,"name:",u.database); print("MAX secret present and not a known placeholder:",bool(s.max_webhook_secret and s.max_webhook_secret.strip() and not s.max_webhook_secret.startswith(("dev-", "replace-with"))))'
docker compose exec -T api alembic current
curl -fsS http://127.0.0.1:8000/ready
```

Остановитесь при ошибках или локальных изменениях Git. Для следующего этапа нужно подтвердить, какая БД и хранилище действительно используются, как устроен HTTPS/proxy, какие контейнеры работают, и что есть место и проверяемые резервные копии. `staging` само по себе не означает отсутствие реальных пользователей. Не выполняйте `docker compose down -v`, `git reset --hard`, массовую перерегистрацию webhook или пересоздание `.env`.

## Порядок обновления после проверки конфигурации

1. Согласовать окно обслуживания, зафиксировать текущий commit и версию миграции. Убедиться, что рабочее дерево чистое, а MAX secret настроен и совпадает с зарегистрированным в MAX. Узнать владельца текущего reverse proxy и TLS.
2. Создать защищённую резервную копию **используемой** PostgreSQL-базы и медиа, а также отдельно защитить конфигурацию (секреты не публиковать). Если БД внешняя, S3 или путь медиа вне стандартного volume — копировать именно их, а не предполагать локальный `postgres`/`var/media`. Проверить непустой дамп, перечень его объектов и восстановление на отдельном экземпляре. Сохранить бэкап вне сервера в подходящем защищённом хранилище, соблюдать ограничения на данные клиентов. Бэкап не проверен, пока не проверено восстановление.
3. Только после этого — `git pull --ff-only origin main` в `/opt/sneg`, пересборка и запуск API/worker тем же Compose-профилем, который используется на данном VPS. Команда API в текущем Compose автоматически выполняет Alembic до запуска сервера. Не запускать несколько независимых миграторов одновременно; оценить миграции между текущей и новой версиями.
4. Проверить состояние контейнеров и локальный `/ready`, HTTPS сайта, вход в админку, журнал ошибок без публикации секретов, вкладку «Сверка платежей» и тестовое сообщение в MAX. При включённой ЮKassa использовать только отдельно согласованный тестовый контур. Не считать `/ready` доказательством работоспособности MAX, ЮKassa или чека.
5. При проблемах остановить действия с заказами/платежами и использовать заранее проверенный план отката кода и схемы. Не откатывать базу до обновления поверх уже созданных заказов без оценки потери данных. Подтвердить наблюдение за очередями и обращениями после запуска.

Нет подтверждения, что эти шаги уже выполнены на VPS. Перед включением реальной новой схемы дополнительно нужны договоры и подтверждённые возможности Консоль.Про, эквайера, юриста и бухгалтера.
